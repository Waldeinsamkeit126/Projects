## 2026-07-12：并发阶梯压测

- 2路、两个不同userId：全部成功，约40–42秒，总墙钟约42秒；
- 5路、五个userId各一路：3个成功（25～193秒），2个在240秒后被服务端断开；
- 3路：全部成功，但耗时分别约71、202、231秒。

结论：白名单ID可以同时使用，但后台存在共享队列/拥塞，吞吐不会随ID数量线性增长。固定5路不安全，固定3路也会在繁忙时严重排队。默认并发保持2；批量调度器应根据滚动成功率和延迟在1～3路间升降，任何断连、429或超时立即降为1并冷却，所有成功结果落盘后才允许重试。

## 2026-07-12：PP-OCRv6 tiny 网格块验证

- 隔离环境：PaddleOCR 3.7.0、PaddlePaddle CPU 3.3.1；检测与识别模型均为 PP-OCRv6 tiny。
- 逐单元格直接送识别模型失败：444 格中仅 55 格完全正确（12.42%），原因是边框、窄图比例和相邻字符污染。
- 连续块不加重叠：396 格中 377 格正确（95.20%），19 个错误全部位于最左或最右核心列。
- 连续块四周增加一圈单元格、只采用核心区：396/396 完全正确，预测约 20.4 秒。
- 换到第 4 张表的另一位置交叉验证：449/450 完全正确（99.78%），预测约 10.9 秒；唯一错误为漏掉一个重复数字。
- 首个标准网格块的完整检测+识别此前为 442/444 完全正确；排除构造方式不同的左上角复合表头后为 99.55%。

结论：极端高密表使用“确定性网格检测 + 带一圈重叠的连续块 + tiny OCR + 坐标归位”；普通表格和长文档继续优先使用官方 FinixDoc-VL。逐格识别路线永久禁用。

## 2026-07-12：长文档切片像素预算

对 100 张训练长文档按 Markdown 字符数与像素数做比例上界估算：3000 万像素块的最密样本约 5616 字符；4500 万约 8424；5500 万与 6000 万的最密样本均约 9400。6000 万的 95 分位已约 8649 字符，距离实测约 1.1 万字符输出上限过近。

结论：纵向块上限从 3000 万提高到 5500 万像素，保留 1000 像素重叠。该值接近已实测成功的 4562 万像素整图，并在训练分布上保留约 1600 字符以上的截断余量。

缩至 2400 万像素后的第二次 API 在有限重试内成功，但输出 11371 字符且 HTML 表格未闭合，确认被接口输出上限截断。图像检查显示它实际是位于页面上部、下方留有大面积空白的三角形高密数值表。旧检测器用整页高度计算竖线覆盖率，未能移除只跨越内容区的表格竖线。检测器改为先求稳健墨迹边界，再在内容框内计算横竖规则线覆盖率。

内容框规则若全局启用，训练表区域数仅 79/100 与 GT 表数完全一致；双路宽松选择为 83/100，严格选择与纯整页算法均为 82/100。此前记录的 91/100 无法由当前审计脚本复现，作废。最终仅在整页块超过 300 万像素、内容框块至少缩小 4 倍、内容框通过全部本地门槛且单元格数不减少时切换；A 榜严格计划仅 4 张使用内容框模式。

三角表修复后得到 86 行、52 列、4472 格，16 个块最大约 65.2 万像素。本地 tiny OCR 用时约 194 秒，输出 60660 字符、86 个闭合 HTML 行、4472 个 `<td>`，无结构警告。批量计划升级为 v3；每张预测元数据包含完整路由签名，任何路由参数变化都会使旧预测失效。存在截断、未闭合表、缺少表格标记或乱码替换字符时，程序拒绝生成提交 CSV。

## 2026-07-15：长图超大重叠拼接修正 v8

批量计划将每个长图块限制在约 5500 万像素，并把最后一块固定到图像底部；当文档高度只略高于一个块时，最后两块会产生远大于计划值 1000 像素的重叠。46 张纵向切片图中，部分末块的实际重叠比例达到 70%–92%。旧拼接器只检查相邻输出边界的 80 行，因此这些大重叠没有被完整删除。
