## 结论与证据

2026-09-18 从天池公开[比赛说明](https://tianchi.aliyun.com/competition/entrance/532510/information)的「4.2 内容提取题和内容推理题答案格式」核实：多结果要求 JSON 数组，数组元素直接是所求具体值。官网示例混用数值和文本值。数组内空缺用空字符串。

现有 `reliable-v3-audited` 的 `buildPrompt` 却要求数组每项是扁平键值对象，且所有字段值转为字符串；`validateAnswer` 会拒绝官网示例。这个偏差值得优先验证，但不能推断所有历史提交都受影响，或直接宣称分数会提高。

使用 Artifact Tool 只读导入 `D:/tests.xlsx`，分析 `Sheet1!A2:F909` 的元数据，没有分析 G 列答案，没有读取正式题目配套图片来手工标注。908 题中 string 409、number 360、json 40、json_array 99。99 道数组题涉及 63 个源文件，约占总题数 10.9%，这不是预计提分幅度。

数组题原始类型为 extract 38、thinking 60，另有 1 行 question_type 误放了题目文本，现有通用规范化已按 extract 处理。本次对题目文本的关键词检索未检出「键值」「键为」「对象数组」「键名」「key-value」「array of objects」等明确对象格式表述。检索不是完整语义证明。

同日公开[排行榜](https://tianchi.aliyun.com/competition/entrance/532510/rankingList)第二页显示第 30 名为 **77.00**。这是当时快照，不是固定门槛。个人成绩页仍跳转登录，当前个人成绩、名次、最后一次实际提交均未重新核实。

## 执行前实现与离线验证

- 独立模块 `array-value-contract.mjs` 仅替换旧提示词的数组格式段。旧核心、缓存身份、历史答案、参考标签及评分器不改。
- 保留数值/文本/布尔类型、零、前导零、空字符串、顺序和重复值；拒绝对象、嵌套数组及 null。不把历史对象数组机械展开为值数组。
- 顺序未指定时按表格阅读顺序输出是候选策略，不是已验证的官方排序实现。当前不推断官方是否容忍数字字符串或其他等价表达。
- 新增 10 道只涉及既有自建合成订单/库存图片的问题，参考独立存放。均由合成表内容建立，不使用正式测试答案。推理请求只携带原图及白名单问题字段，参考文件仅校验哈希、不解析到请求。
- 两张合成图已人工目视核对本地参考。这是可见开发材料上的格式冒烟检查，不是盲测、独立新表留出集或同预算 A/B。
